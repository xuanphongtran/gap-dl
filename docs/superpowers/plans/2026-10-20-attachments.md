# Chat Attachments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with the preserved native/inline workflow. Steps use checkbox (`- [x]`) syntax for tracking. One independent final whole-branch reviewer; no per-task implementation/review agents.

**Goal:** Let room members upload/process up to five supported files, explicitly send them with a caption and optional mentions, and download live message attachments without weakening retry identity or account privacy.

**Architecture:** A focused upload composable owns ephemeral file/ticket state and account-scoped metadata queries. Extend the existing immutable send-intent owner rather than creating a second sender; share attachment rendering/download across history and Search. Deterministic native fixtures prove frontend behavior independently of a separate live service-readiness gate.

**Tech Stack:** Vue3, TypeScript, Axios, Vue Query, VueUse, Vitest, Web Crypto, native Chrome CDP, npm, Node >=22.18.0. No new runtime dependencies.

**Spec:** [Approved attachment design](../specs/2026-10-20-attachments-design.md), approved by the user on 2026-10-20. [Contract/runtime evidence](../../ATTACHMENTS_RECHECK_2026-10-20.md) records the published contract and failed account setup. This implementation plan awaits user review before execution.

## Global Constraints

- Work on existing `feat/attachments` from accepted spec commit `256959e`; preserve the existing-checkout/new-branch preference. Check user changes before edits; no new worktree, push, merge or deploy.
- English source/UI/tests/docs; pixel tokens, accessible labelled native controls, keyboard focus and 390px mobile layout. Base components cannot import API/router/session modules.
- Keep endpoints in `src/lib/api.ts`, transports in `src/lib/http.ts`, cache keys in `src/lib/query.ts`, Pinia session-only. Use Vue Query for safe server state/mutations; files and signed tickets never enter mutation variables/results/context or persistent storage.
- Supported files: compatible PNG/.png, JPEG/.jpg/.jpeg, text/plain/.txt;1–10,485,760 bytes/file, maximum 5 selections. Filename1–255 UTF-8 bytes, no control characters/path separators. Empty MIME is accepted only for .txt as text/plain. Server processing remains authoritative.
- Hash original bytes using Web Crypto SHA-256, serialize active hashing/transfers, retain at most 5 File objects and release raw references at ready/removal. Processed output may differ in size/hash.
- Require nonblank trimmed caption <=4,000 UTF-8 bytes in this frontend slice. Render inbound file-only/empty-after-uploader-deletion messages. No attachment-only creation, previews, drag/paste/multipart, file-content search, antivirus claim, presence/typing, SSE or distributed guarantees.
- Use separate upload/message UUID keys; never automatically replay writes. Freeze caption/mentions/file IDs/key on uncertain send. Keep existing 24h retry bound; no automatic rekey after409 or ambiguous results.
- Processing202/upload100% is not verification. Poll authorized metadata every 2s while active/visible/online, stop after 60s active observation with CHECK STATUS. Valid Retry-After gates all poll/focus/manual attempts by maximum absolute deadline; unknown states stay non-sendable.
- Download tickets are obtained only on click, HTTPS only, no prefetch/cache/log/persistent link. Use fresh60-second download navigation with noreferrer/noopener; no API JWT on storage requests. Issued links are not instantly revocable.
- Room navigation discards unsent file selections while preserving ordinary text drafts; pending keyed sends retain safe snapshots. Never cancel IDs owned by pending/uncertain sends. Account/access changes abort/hide work before late callbacks; no cleanup using a new account's token.
- Full local implementation/checks may complete while BE readiness is unavailable. Live acceptance and release remain open until response-backed verification; no readiness failure may be replaced with a simulated pass.
- No account/quota/rate-limit flood, malicious scanner sample, restart, migration or schema rollback. Physical delayed cleanup/quota release is separate from a204 cancellation acknowledgement.

## Review Focus

1. A ready-file send receives a definite400/429 before uncertainty: caption and ready files remain editable; transferring upload ownership must not lose them (Task3).
2. User changes account between reservation acceptance and cancellation: late upload metadata/tickets cannot be cached or cancelled with the new token (Task2).
3. A file binding disappears with404 while room access remains valid: mark only that file unavailable, without erasing the room or draft (Task4).
4. An uncertain send is discarded or its room closes: no cancellation removes possibly accepted attachments, and a canonical retry cannot be duplicated (Tasks2/3/5).
5. Native fixtures need HTTPS tickets while external network stays blocked: interception must fail closed, preserve HTTPS validation and never reach the deployed API (Task5).
